The X "For You" Algorithm

A complete architectural deep-dive of the recommendation system powering the "For You" feed on X — how a request becomes a ranked timeline, end-to-end and at the algorithm level.

The Core Idea

The system retrieves posts from two worlds — in-network (accounts you follow, served by Thunder) and out-of-network (a global corpus, served by Phoenix retrieval) — then ranks them all together with Phoenix, a Grok-based transformer that predicts how you'll engage with each post. The headline design philosophy: every hand-engineered relevance feature and most heuristics were deleted. The transformer reads your raw engagement history and figures out relevance itself.

Two Candidate Sources

In-network recency (Thunder, sub-ms in-memory) + ML similarity search over millions of posts (Phoenix two-tower).

One Ranking Brain

A Grok-1-derived transformer predicts ~19 engagement probabilities per post with strict candidate isolation.

Composable Orchestration

A generic candidate-pipeline engine wires sources → hydrators → filters → scorers → selector.

02 The Candidate-Pipeline Engine

Every recommendation flow in the system is an instance of one generic Rust framework (candidate-pipeline/). It defines a fixed set of stage traits and a single execute() method that runs them in a fixed order with a deliberate concurrency model. Business logic plugs in as trait objects; the engine owns execution, parallelism, error isolation and metrics.

The stage traits lib.rs

  • QueryHydrator<Q> — fetch user/request context
  • Source<Q,C> — produce candidates
  • Hydrator<Q,C> — enrich candidates
  • Filter<Q,C> — drop candidates
  • Scorer<Q,C> — assign/modify score
  • Selector<Q,C> — sort & cut to top-K
  • SideEffect<Q,C> — async fire-and-forget

Error isolation

A source/hydrator/query-hydrator that returns Err is simply skipped — the pipeline degrades gracefully rather than failing the request. A scorer/hydrator that returns a wrong-length result is dropped wholesale (length contract). The whole execute() is wrapped in a latency-bucketed stats macro.

03 Home Mixer Rust

The orchestration layer. It exposes gRPC services, builds a per-request ScoredPostsQuery, and runs the two stacked candidate pipelines. The server boots an XServiceBuilder with mTLS, gzip+zstd, dark-traffic layers, and wires one PhoenixCandidatePipeline inside one ForYouCandidatePipeline.

Request entry & the QueryBuilder

Reject anonymous — viewer_id == 0 is refused immediately.
Fetch viewer data — Gizmoduck call with a hard 200 ms timeout; on timeout/error falls back to default viewer data so the request still proceeds.
Resolve in-network-only — true if the request asks for it OR the viewer has opted out of recommendations.
Evaluate feature switches — a RecipientBuilder keyed on user/country/language/app/datacenter/account-age/roles materialises all runtime params (weights, thresholds, cluster IDs).
Build query — generate prediction_id/request_id; mark ~50% of traffic as shadow for experiment replay.

The cache short-circuit

When a user has ≥ ~500 cached scored posts, has_cached_posts disables all live sources/hydrators/the Phoenix scorer — only CachedPostsSource runs, feeding already-scored candidates straight to the selector. This is the cheap path for rapid re-requests / pagination.

Finally the engine truncates to RESULT_SIZE.

⑧ Side effects — 6, detached

Shadow-traffic Phoenix experiment replay, reranking-Kafka sampling, Redis post-candidate caching (zstd, ~180 s TTL), score-distribution stats, mutual-follow stats, and a two-cluster Phoenix request cache. None of these touch the response.

04 Thunder — In-Network Store Rust

An in-memory post store + realtime Kafka ingestion pipeline. Its single job: given a viewer's follow list, return recent posts from those accounts in sub-millisecond time, with no external database on the read path.

Retention & trimming algorithm

Default retention 2 days. Three eviction mechanisms:

  1. Insert-time filter — posts in the future or older than retention never enter the store.
  2. Delete-event filter — delete events for already-trimmable posts are skipped.
  3. Periodic auto-trim — a background task every 2 minutes (on spawn_blocking) walks each user deque from the front (oldest) popping expired posts and breaking at the first fresh one — O(evicted) per user because deques are time-sorted. It also reclaims over-allocated deque capacity and removes empty users.
Lazy delete

A delete does not scan and remove from timelines (expensive). It removes from posts, sets a tombstone, and pushes the tombstone under a synthetic DELETE_EVENT_KEY "user" so it's trimmable on the same clock. The stale TinyPost in timelines is filtered out lazily at read time and physically reaped by the trimmer.

The serving / query path

Admission control — non-blocking semaphore try_acquire; over capacity → immediate RESOURCE_EXHAUSTED (load-shed, never queue).
Gather on spawn_blocking — for each followed user (capped), iterate their deque newest-first, copy LightPost out of the map immediately (release shard lock fast, avoid nested-lock deadlock), apply per-author scan cap.
Filter — drop tombstoned ids, drop self-retweets, and for replies apply a reply-context filter (keep only replies into root posts or followed conversations).
Per-iteration wall-clock timeout — bounds tail latency: return whatever was gathered so far rather than blow the deadline.
Score & truncate — sort all gathered posts by Reverse(created_at) and take max_results. Ordering is pure recency — Thunder does no ML.

Sub-ms is achieved by: DashMap shard-level locking, copying out of locks immediately, bounded per-author/per-request work, the read path on spawn_blocking, and the write path throttled (a 3-permit semaphore post-init) to leave CPU for reads.

The shared trick: hash-based embeddings

There is no per-ID embedding row. Each 64-bit entity ID (user, post/item, author) is passed through 2 independent linear-congruential hash functions into a shared embedding table — the "hashing trick" / Bloom embeddings. Bucket 0 is reserved for padding/invalid.

raw = (id * scale[j] + bias[j]) mod modulus
bucket[j] = 0 if id==0 else (raw mod (num_buckets-1)) + 1
# j ∈ {0,1}; user/item/author each have their own scale,bias and a 1,000,000-row vocab region

All three entity types share one monolithic table; per-entity hashes are offset into disjoint index ranges. Multi-hash vectors are combined per token by a learned projection in three "reduce" blocks (user / history / candidate), which also fold in action, product-surface, dwell-time and post-age embeddings.

06 Retrieval — The Two-Tower Algorithm

Two-tower models split the score into sim(user_vec, item_vec) so item vectors can be precomputed offline and searched with fast ANN — the only way to consider millions of posts per request.

User Tower (online)

  1. Build user + history embeddings (post⊕author⊕action⊕product-surface) via reduce blocks
  2. Concat [user, history] → run the Grok transformer with a causal mask (no candidates here)
  3. Mean-pool over valid (non-padded) positions
  4. L2-normalise → u ∈ ℝᴰ

Candidate Tower (offline)

  1. Concat candidate post ⊕ author hash embeddings
  2. 2-layer SiLU MLP projection (or mean-pool over hashes)
  3. L2-normalise → every corpus post becomes a unit vector
  4. Whole corpus precomputed: ~537K posts in the released sports demo

Similarity search

Because both towers are L2-normalised, dot product = cosine similarity:

scores = u · corpusᵀ   # [N] cosine similarities
top_k_idx = argpartition(scores)[-K:] → sort desc   # K = --top_k_retrieval, default 200

The released pipeline does exact brute-force dot product over the corpus; production uses ANN. The retrieved post IDs (with author IDs and topics) become the candidate set handed to ranking.

The candidate-isolation attention mask

This is the system's most important architectural decision. Start from a causal (lower-triangular) mask, then zero the entire candidate↔candidate block, then restore only the diagonal so each candidate can still self-attend.

Why isolation matters

A candidate's score depends only on the user context, never on which other posts happen to share the batch. This makes scores deterministic, batch-invariant and cacheable, and lets you score any subset of candidates without re-running the rest.

Output head — multi-action prediction

After the final RMSNorm, only the candidate positions are sliced out and projected by an unembedding matrix into ~19 action logits; sigmoid gives independent per-action probabilities (multi-label, not softmax). A separate continuous head predicts 8 regression targets (dwell time, watch time, scroll depth…).

cand = RMSNorm(transformer_out)[:, candidates, :]  # [B, C, D]
logits = cand @ unembeddings  # [B, C, num_actions]
P(action) = sigmoid(logits)

Ranking forward pass — algorithm-level pseudocode 
function PhoenixRank(user, history, candidates):
    # --- build input segments via reduce blocks ---
    u  = block_user_reduce(user_hashes)                         # [B,1,D]
    h  = block_history_reduce(post,author,action,psurf,dwell,age)# [B,S,D]
    c  = block_candidate_reduce(post,author,psurf,age)           # [B,C,D]
    X  = concat([u, h, c], axis=1)                               # [B, 1+S+C, D]
    M  = concat([u_mask, h_mask, c_mask], axis=1)
    cso = 1 + S                                                  # candidate start offset

    # --- candidate-isolation mask ---
    A = tril(ones(T,T))            # causal
    A[cso:, cso:] = 0              # no candidate ↔ candidate
    A[diag(cso:T)] = 1             # restore self-attention
    mask = M[:,None,None,:] * A

    # --- Grok transformer ×N ---
    for layer in 1..N:
        a = MHA(RMSNorm(h), mask)  # RoPE(Q,K); logits*0.125; 30*tanh(./30); softmax fp32
        X = X + RMSNorm(a)
        d = GeGLU(RMSNorm(X))      # Linear( gelu(W1·x) ⊙ V·x )
        X = X + RMSNorm(d)

    # --- action heads on candidate positions only ---
    cand   = RMSNorm(X)[:, cso:, :]            # [B,C,D]
    logits = cand @ unembeddings               # [B,C,num_actions]
    return sigmoid(logits), sigmoid(cand @ continuous_unembeddings)

PhoenixScorer — the model call

Resolves a Phoenix inference cluster (new-user clusters, A/B deciders), builds one prediction request packing the entire candidate batch + the user scoring sequence, and makes a single predict() call (with an egress-sidecar → direct fallback). Per-candidate scores are keyed by original tweet id (retweet collapses to source). Candidate isolation is enforced inside the model, not here. On total failure every candidate gets default scores and the scorer is skipped.

RankingScorer — the four-step combination

1 · Weighted sum

Each action probability is multiplied by a feature-switch weight and summed. Positive actions have positive weights; negative-feedback actions have negative weights.

combined = Σ P(actionᵢ) · weightᵢ
positive_sum = Σ positive weights  ·  negative_sum = −Σ(not_interested,block,mute,report,not_dwelled)
total_sum = positive_sum + negative_sum

vqv/quoted_vqv weights are gated on the candidate's video duration qualifying. Continuous predictions (dwell_time, click_dwell_time) get their own weights.

2 · Negative-offset normalization

Maps the negative range below all positive scores, then shifts positives up by a constant offset — so any post the user would dislike sorts beneath every post they wouldn't.

if total_sum == 0: score = max(combined, 0)
elif combined < 0: score = (combined + negative_sum) / total_sum · NEGATIVE_SCORES_OFFSET
else: score = combined + NEGATIVE_SCORES_OFFSET

Then passed through an external normalize_score().

3 · Author-diversity attenuation

Candidates are ranked by weighted score; for each author a 0-based occurrence counter position is tracked in that order. Each repeated post by the same author is geometrically attenuated toward a floor — the author's best post is untouched (×1), subsequent ones decay.

multiplier(pos) = (1 − floor) · decaypos + floor
adjusted = weighted_score · multiplier(author_position)

4 · Out-of-network adjustment

Diversity-adjusted scores for OON posts are multiplied by an effective OON weight factor (a topic-request / new-user / default variant). In-network and self posts are unchanged.

effective_oon = TopicOonWeight (topic req) | NewUserOonWeight (new user) | OonWeight (default)
final = (in_network == false) ? adjusted · effective_oon : adjusted

VMRanker — optional value-model re-rank

If enabled, sends all candidates' raw Phoenix scores + the RankingScorer output + light features to an external value-model service, with optional DPP (Determinantal Point Process) diversity parameters, and replaces score with the returned value (falling back to the prior score on miss/failure).

Net pipeline

Phoenix per-action probabilities → linear weighted sum → negative-offset normalization → score-normalizer → author-diversity geometric attenuation → OON multiplicative discount → (optional) value-model + DPP re-rank → the score the selector sorts on.

11 End-to-End Request Walkthrough

Putting all five components together — what actually happens when your phone asks for the For You feed:

Request arrives at home-mixer's gRPC ForYouFeedService with your viewer_id. The QueryBuilder fetches viewer roles (200 ms budget), resolves feature switches, builds a ScoredPostsQuery.
For You pipeline runs; its ScoredPostsSource invokes the inner Scored-Posts pipeline.
Query hydration (15 parallel) — your engagement sequences, follow / block / mute / subscribe sets, topics, IP, impression bloom filter are fetched concurrently.
Sourcing (6 parallel) — Thunder returns recent in-network posts from sub-ms in-memory store; Phoenix retrieval embeds your history into a user vector and dot-products it against the precomputed corpus for top-~200 out-of-network posts; TweetMixer / MoE / topics sources add more.
Hydration (10 parallel) — core data, author, media, quote, language, and Grox-derived brand-safety signals are attached to each candidate.
Filtering (14 sequential) — duplicates, over-age, your own posts, already-seen/served, muted keywords, blocked authors are removed.
Scoring — PhoenixScorer sends all surviving candidates + your scoring sequence in one batched call to the Grok ranking transformer (candidate-isolated) → ~19 engagement probabilities per post. RankingScorer collapses them into one score via weighted sum → negative-offset normalize → author-diversity decay → OON discount. VMRanker optionally value-model re-ranks with DPP diversity.
Selection — sort by final score, keep top-K.
Post-selection — visibility filtering (deleted/spam/gore via Grox labels), conversation dedup; truncate to result size. Side effects (caching, logging) fire detached.
Blending — back in the For You pipeline, the BlenderSelector weaves in ads (brand-safe adjacency), who-to-follow, prompts, pinned post → the final ordered timeline returned to your device.

12 Key Design Decisions

No hand-engineered features

Relevance is learned end-to-end by the transformer from raw engagement sequences. Drastically simpler data & serving pipelines.

Candidate isolation

Attention mask forbids candidate↔candidate attention → batch-invariant, deterministic, cacheable scores.

Hash-based embeddings

Multiple hash functions into a fixed shared table — no unbounded per-ID vocab, handles the open-world ID space.

Multi-action prediction

Predict ~19 independent action probabilities, not one relevance scalar — negative actions explicitly push bad content down.

Two-stage retrieval→ranking

Cheap dot product narrows millions → hundreds; expensive transformer ranks the few. The only tractable shape at scale.

Composable pipeline

One generic engine, fixed stage order, explicit parallel/sequential contract, graceful per-component error isolation.

This is a partial open-source release

  • home-mixer's params (all *Weights, RESULT_SIZE, TOP_K_CANDIDATES_TO_SELECT, MAX_POST_AGE, NEGATIVE_SCORES_OFFSET, OON/diversity factors) and clients are runtime feature-switch / external modules.

  • scorers/weighted_scorer.rs, author_diversity_scorer.rs, oon_scorer.rs are superseded dead code (absent from scorers/mod.rs); the live logic is consolidated in RankingScorer.
